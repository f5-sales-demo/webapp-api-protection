Terraform prepares the origin, traffic generator and F5 Distributed Cloud protection resources.
Use the guarded lifecycle commands from the repository root. Keep the same private state
directory throughout deployment, demonstrations and cleanup.

## Prerequisites

Install Terraform 1.8 or later, Python 3, Azure CLI, SSH, cURL and dig.
The DVWA walkthrough also requires Node.js, Playwright and its installed Chromium browser
on the operator host. Its offline marker check disables outbound browser requests. Use an authenticated
Azure CLI human user in the approved subscription and Microsoft Entra tenant, existing
F5 Distributed Cloud credentials and an SSH key pair. The namespace must already exist.
The lifecycle verifies the selected identity, permissions, feature entitlement, quota and DNS.
It does not create a login workflow or collect credentials.

Create the private operator file outside the checkout. Its directory must have mode 0700;
the non-symlink file must have mode 0600.

```json
{
  "subscription_id": "<APPROVED_SUBSCRIPTION_ID>",
  "tenant_id": "<APPROVED_TENANT_ID>",
  "expected_azure_user": "<APPROVED_AZURE_USER>"
}
```

The default location is `~/.local/state/waap-showcase/operator.json`. Supply approved values
privately. State and receipts live under the approved subscription directory. An explicit
`--config` replaces the default operator file; `--state-dir` chooses data location only.
See [state and restoration](../reference/state-and-restoration/) for precedence, locking,
backups and recovery.

The profile uses `eastus2`, an origin `Standard_D16s_v3` and a generator `Standard_F16s_v2`.
It deploys no Customer Edge, AWS or Google Cloud resources. Local Terraform backends require
no Azure storage account or blob role. Shared DNS, the namespace and the versioned schema
fixture are preserved. Provider locks pin the reviewed dependencies, including xcsh 13.0.3.

## Deploy

```bash
bash scripts/demo-lifecycle.sh deploy
```

Deploy verifies scope, initializes private state, reconciles the existing namespace, applies
a guarded application plan and installs the immutable application and traffic sources.
Readiness requires application and replica checks. Security acceptance separately requires
fresh control attribution; a successful Terraform plan cannot prove protection.

## Verify

```bash
bash scripts/demo-lifecycle.sh verify
```

Verify reads existing state, checks the preserved namespace and requires zero drift. It does
not import, apply or repair infrastructure. Missing telemetry returns an incomplete result.
The follow-up reconciled historical snapshots and the exact deployed schema receipt;
backend, ownership and fixture preflight now pass. Open a walkthrough window only after
current installed readiness also passes.

## Present a use case

Pause continuous traffic using [traffic operation](../reference/traffic/). Follow one article,
using fresh synthetic identities and complete configuration snapshots. The category harness
uses API GET and PUT operations; it does not apply Terraform during the comparison.
Restore the original configuration before the next category. Capture date, revision, receipt
identifier and measured duration belong to the run, not a generic time estimate.

## Clean up

```bash
bash scripts/demo-lifecycle.sh destroy
```

Destroy removes only owned application resources. It preserves the namespace, schema fixture,
shared DNS and existing Azure storage. It retains private state and receipts for recovery.

Use `bash scripts/demo-lifecycle.sh rebuild` only for an authorized clean rebuild: it deletes
owned applications, proves their absence and redeploys them. Rebuild and destroy are deliberate
destructive operations. Their ownership gates must complete; do not bypass them with raw
Terraform apply or destroy commands.
